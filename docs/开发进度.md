## 3. 关键实现要点（下次开发必读）

### 后端、作业与发布边界

- 鉴权链为 CSRF 发放、Origin/CSRF 校验、HttpOnly Cookie 会话；route-aware request-body gate 已按规范化路由标签聚合。

- 会话列表以 `created_at DESC, id DESC` keyset 分页；消息历史按最新优先查询、页内升序返回并以前插方式继续加载。游标为版本化 base64url JSON，列表/消息 scope 隔离，消息页绑定会话；非法游标统一返回固定 `UNPROCESSABLE` 422。
- durable jobs、sqlite-vec/hash-v1 候选、RAG SSE、备份/恢复、结构化可观测性与 Compose/Caddy/release gate 均已存在；真实 GGUF、授权语料、真实运行时与恢复验收未完成。

### 已修复并覆盖

## 15. 2026-08-29 RAG 向量化基础设施与独立验证

本节只追加本轮 RAG 向量化基础设施的已实现事实、独立验证证据和外部门禁。它表示 W7/W8/M3 的基础设施推进，不表示 M3、W7 或 W8 已全部完成，也不表示系统已可生产部署。

### 已实现的基础设施

- API 依赖固定为 `sqlite-vec==0.1.9`；数据库已推进到 schema v2。向量数据使用常规 BLOB 表 `chunk_embedding` 保存 float32 序列化结果，并通过 sqlite-vec 的 `vec_distance_cosine` 完成同 profile 的距离检索。
- 运行时 sqlite-vec 扩展加载、向量 BLOB 序列化/查询及 `chunk_embedding` 的应用访问收敛到 `VectorStore`；schema 迁移、备份校验和评测只读取其明确的数据契约。v1 遗留的无法满足完整 sqlite-vec ref/BLOB/profile 约束的 ready 文档会保留历史行并转为 queued，标记 `INDEX_REBUILD_REQUIRED`。

- worker 在写入前完整生成并校验 embedding batch，并在同一原子边界内替换旧 chunk/vector ref/BLOB、核对计数并把文档置为 ready。最终失败或陈旧 running job 耗尽重试次数时，job 与未删除文档会同步标为 failed；ingest/purge 也会严格校验 payload 的 assetId 与数据库文档关联一致。

## 18. 2026-08-30 M2 私有原始 MIME 分层归档本机验证

本节仅记录隔离本机的 schema v4、接收、保留期和备份实现；它推进 M2 的本地候选链，不表示 M2 完成，也不代表真实 Cloudflare、MX、域名或生产 60 秒可见性门禁已经验收。

## 19. 2026-08-30 schema v5 通用 asset GC 本机候选验证

本节只记录隔离临时 `DATA_ROOT` 中的实现与复验。它推进 M2/M3 的本地对象生命周期候选链，不表示任何 M 里程碑完成，也不表示已部署、已接管真实邮件存储或已完成生产并发备份门禁。

- SQLite 已推进到 schema v5。`asset` 只有一个 `storage_class`：`unknown`、`file`、`photo-original`、`photo-thumbnail`、`knowledge`、`mail-attachment`；同时记录 `object_purged_at`、`gc_next_run_at`、非负 `gc_attempts` 和 `gc_error_code`。v1/v2/v3/v4 均按真实迁移链进入 v5，未来版本、缺列、缺 CHECK 和削弱的 GC 索引均拒绝启动。

## 20. 2026-08-31 SQLite 备份协调与对象快照清单

本节只记录隔离临时 `DATA_ROOT` 的实现与自动化验证；它关闭协作型 SQLite 写者与对象复制之间的已知混合时点窗口。备份/restore 本身不构成恢复演练；受控本地候选 runner 的约束见第 21 节，仍不表示 M2 已完成。

### 已实现

- `backup_restore.py` 保持 manifest format v3、schema v5 与 format v2/v3 的既有 restore/verify 兼容。备份先检查 source SQLite，再由连接 A 获取有界 `BEGIN IMMEDIATE`；独立只读连接 B 使用 online backup API 生成 destination snapshot。A 会持有至 SQLite、按逻辑清单复制的对象和原子 manifest 全部完成，释放后才执行可选 verify。

## 36. 2026-09-02 route-aware raw ASGI request-body gate（Sol 终审通过；本地候选）

本节记录 Terra 在 pytest 临时 `DATA_ROOT` 与本机隔离 browser E2E 上的实现/验证候选，以及其后的 Sol 独立终审；本地通过不代表 HTTP/2、Caddy、Docker、部署或生产流量已经验证。

### 方案、预算与错误优先级

- 新增纯 ASGI `RequestBodyLimitMiddleware`，在 `request_context` 注册前通过 `app.add_middleware(...)` 安装，因此实际栈为 ServerError → request_context → body limiter → ExceptionMiddleware → Router。直接 400/413 仍由外层安全 request ID、`X-Request-Id` 和 `request_completed` JSONL 覆盖。
- policy 在 app 创建时一次性快照当前 settings 与 `knowledge.DOC_MAX_BYTES`：POST files/photos/documents 分别为既有业务上限加 64 KiB multipart overhead；mail 为 `mail_max_bytes` 无 overhead；RAG 为 128 KiB；login/conversations/document rebuild/mail read 为 64 KiB。其它 FULL 匹配 route 与 OPTIONS 为 0，method mismatch/unmatched 为 64 KiB fallback，不能取得上传宽预算。既有 endpoint-local payload 限制未删除，仍是第二道防线。
- 运行时使用 FastAPI 公共 `iter_route_contexts(app.router.routes)` 的逐项 `matches(scope) == FULL` 取得 canonical route；保留旧版 FastAPI 的扁平 `router.routes` fallback。尾斜杠只在原 scope 无 FULL 时复制 scope 并按 Starlette 规则切换后重新要求 FULL；没有使用 raw URL/startswith。早期拒绝仅把已匹配 route context 放入 `scope['route']`，供安全 route template 遥测使用。
- framing 先于任何 receive/parser/auth/CSRF/endpoint：重复或非 ASCII 十进制/空/超过 20 位 Content-Length，以及任一 Transfer-Encoding + Content-Length 固定 400 `BAD_REQUEST`；可信单一 CL 超预算固定 413 `PAYLOAD_TOO_LARGE`，均不调用 receive/downstream。HTTP/1.0/1.1 加 `Connection: close`，HTTP/2 不加。错误体固定为统一 `{error:{code,message,requestId}}`，不回显 header/body/path/filename。
- CL 不大于 cap 时仍逐 `http.request.body` chunk 计数；raw bytes 指当前 ASGI 栈收到的 body bytes，包含 multipart boundary/part header，gzip 等 Content-Encoding 计编码后的 entity bytes，不包含 HTTP chunk/H2/TCP/TLS framing。无 CL 的实际消费流在 cap+1 中断；体积/非法 framing 优先于 auth、HMAC、CSRF 与业务校验。

### multipart、异常归一与已知物理边界

- receive-time overflow 同时继承 `fastapi.HTTPException` 与 `MultiPartException`，携带仅进程内 identity marker。这样 JSON/raw 进入内层统一 HTTP handler；multipart 路径让 Starlette 关闭已建 SpooledTemporaryFile，再将 marker 转成基类 HTTPException，由 main 的 Starlette-base handler 正规化回 413，marker 永不序列化。使用 FastAPI HTTPException 子类还使既有 mail `_read_limited_body` 的 re-raise 分支不把 overflow 落入 broad-except 变成 503。
- 实际 files/photos/knowledge 的无 CL multipart 分块回归先创建一个 tiny spool，再在 cap+1 前中断；确认 spool 已 close，且 asset/photo/document/job/audit/mail 计数及 pytest 临时对象集合无持久副作用。现用 venv 的 MultiPartParser 已在 `BaseException` 时关闭 spool；双继承仍兼容只捕获 `MultiPartException` 的较旧实现。
- 该 gate 有意为 lazy receive：无 Content-Length 且下游从不调用 receive 的 bodyless、wrong-content-type 或 unmatched 请求，无法观察完整 body；没有完整预读、缓存或拼接 body。对真实 parser/stream 消费的无 CL 流，最多可能已有不超过 cap 的 multipart 前缀写入 spool，但会关闭且不会进入持久 DB/storage/object/job。
- response 已开始后才继续读取并超限时，middleware 只传播异常、不伪造第二个 response start；synthetic ASGI 回归确认没有第二个 start。未在本轮宣称真实 HTTP/2 transport、Caddy 或部署层的 connection/drain 行为。

## 47. 2026-09-06 照片时间语义与并发一致性复验

本节是 §46 之后的最新增量快照。§46.6 中关于“照片 EXIF/ISO 混合字典序仍待冻结策略”的结论是当时事实；本节已冻结最小、无迁移语义并完成实现与回归。详细总览仍见 [2026-09-05 现状分析与验收报告](./2026-09-05_现状分析与验收报告.md)。

### 47.1 缺陷证据与语义决策

- API 原先把 Pillow 的 `DateTimeOriginal` 原样写成 `YYYY:MM:DD HH:MM:SS`。Windows Chrome/Edge 与 Node 对该字符串均返回 Invalid Date，前端 `formatDate` 随即回显完整秒级字符串，导致同一天不同时刻被拆成多个时间轴分组。
- SQLite 原排序键为 `COALESCE(capture_at, created_at)`。默认 BINARY 比较中 `:` 大于 `-`，legacy EXIF、canonical capture 和 ISO fallback 并非按时间语义排列；既有 `idx_photo_capture` 也不能覆盖该表达式排序。
- `DateTimeOriginal` 缺少时区时只代表相机当地墙钟时间。当前决策是不附加 `Z`、不套用服务器/浏览器时区、不使用 `OffsetTimeOriginal` 猜测历史 instant；严格合法值统一为 `YYYY-MM-DDTHH:MM:SS`，非法或缺失值归入“未知日期”。如未来需要绝对时间，须另设带 offset 的字段和迁移方案。
- 有效拍摄时间与未知时间不再直接比较：有效组先展示并按 canonical capture 倒序；未知组随后按 UTC `created_at` 倒序。该顺序与 UI 的独立“未知日期”分组一致。

## 48. 2026-09-07 照片真实 Exif、方向校正与 E2E 数据边界终审

本节是当前最新统一快照，覆盖 §47 后的独立反例复核、修复与全量复验。第 8–47 节继续按当时事实保留；当前综合分析、差距矩阵与验收表见 [2026-09-05 现状分析与验收报告](./2026-09-05_现状分析与验收报告.md)。

### 48.1 终审发现的直接反例

- 标准相机通常把 `DateTimeOriginal`（`0x9003`）放在 Exif 子 IFD（顶层只含 `0x8769` 指针）。§47 当时的 Pillow fixture 把 `0x9003` 直接写在顶层，掩盖了真实结构；内存探针证明旧提取器对标准 nested IFD 返回 `None`。
- 带 Orientation=6 的 JPEG 原始 header 为 8×12，但视觉方向为 12×8。旧缩略图直接 `convert("RGB")` 会丢弃 Orientation 元数据而不旋转像素，导致竖拍图横倒，数据库宽高也与视觉方向不符。
- 照片 fixture 新增后，隐藏 CLI 参数本身不能充当隔离边界：直接把 `--isolated-fixture-db` 指向调用方数据库会使外部服务模式具备写入路径。该反例违背“外部模式不触碰调用方数据库”的既有约束。
- Web 若把无时区墙钟值构造成宿主 `Date`，在 DST gap 等本地时区规则下仍可能被规范化到另一个时刻。照片日标签不需要 instant，因此应直接验证字段和 Gregorian 日历，不创建 `Date`、不经 locale/timezone。
