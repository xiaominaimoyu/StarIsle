# 本地运行与恢复指南

更新：2026-11-03。供项目所有者在本机启动私有空间、备份和切换恢复数据。公开网站由 Cloudflare Pages 承载；本指南不把本机运行写成私有云、生产 TLS、真实邮件或模型验收。

下面的命令由你在仓库根目录执行，只使用你明确选择的配置和绝对数据路径。代码示例不会显示配置文件内容。实际检查结果以 [本轮验收报告](./2026-11-03_网站交付与本地恢复验收.md) 为准；操作指南本身不声明验收通过。

## 开发时同时启动三个进程

前提是现有 pnpm 依赖和 `apps/api/.venv` 可用。新环境才需要在 `apps/api` 执行 `python -m venv .venv`，然后用该虚拟环境的 Python 安装 `requirements.txt`；已有环境不要重复重建。由所有者从 `.env.example` 建立本机配置，填入随机 JWT/HMAC 密钥和管理员 Argon2id 哈希，并将 `DATA_ROOT` 指向选定的外置绝对目录。不要覆盖既有配置、向聊天发送密码或将实际配置提交到 Git。

新环境安装 API 依赖时，进入 `apps/api` 后使用同一解释器：

```powershell
# 仅用于尚无 .venv 的新环境。
python -m venv .venv
& .\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

在两个独立终端中，分别进入仓库的 `apps/api`。API 与 worker 使用同一工作目录和配置：

```powershell
# 终端 1，当前目录为 apps/api。
& .\.venv\Scripts\python.exe -B -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload --no-access-log
```

```powershell
# 终端 2，当前目录同样为 apps/api。
& .\.venv\Scripts\python.exe -B -m app.worker_runner
```

第三个终端在仓库根目录运行 `pnpm dev`，访问 `http://localhost:4321`。文档上传后须看到 worker 将状态推进至 ready；只有 API/Web 启动不代表索引和维护正常。开发完成后在各自终端停止本轮进程。

管理员哈希仅用于首次创建账户。数据库中已有管理员时，修改 `ADMIN_BOOTSTRAP_PASSWORD_HASH` 不会替换其密码；恢复后也应使用备份时的账户凭据。

## 用 Compose 提供本机单入口

前提：Linux Docker 引擎已启动；已准备不包含示例密钥的本机 API 配置文件。所有入口仅绑定 loopback。示例固定使用独立项目 `starisle-local`；若你已有其他项目在使用同一端口或数据目录，先核对其项目名和实际配置，不接管它。

在仓库根目录建立本次终端会话变量：

```powershell
$repoRoot = (Get-Location).Path
$runtimeInput = Read-Host '已存在的私有数据根绝对路径（不能在仓库内）'
$workInput = Read-Host '维护工作目录绝对路径（与数据根彼此不包含，不能在仓库内）'
if (-not [IO.Path]::IsPathRooted($runtimeInput) -or -not [IO.Path]::IsPathRooted($workInput)) { throw '需要绝对路径' }
$runtimeRoot = (Resolve-Path -LiteralPath $runtimeInput).Path.TrimEnd('\', '/')
$workRoot = [IO.Path]::GetFullPath($workInput).TrimEnd('\', '/')
foreach ($chosenRoot in @($runtimeRoot, $workRoot)) {
  if ($chosenRoot -eq [IO.Path]::GetPathRoot($chosenRoot).TrimEnd('\', '/')) { throw '不能使用磁盘根目录' }
  if ($chosenRoot -eq $repoRoot -or $chosenRoot.StartsWith($repoRoot.TrimEnd('\', '/') + '\', [StringComparison]::OrdinalIgnoreCase)) { throw '请选择仓库之外的目录' }
}
if ($runtimeRoot -eq $workRoot -or $runtimeRoot.StartsWith($workRoot + '\', [StringComparison]::OrdinalIgnoreCase) -or $workRoot.StartsWith($runtimeRoot + '\', [StringComparison]::OrdinalIgnoreCase)) { throw '数据根与维护根必须彼此独立' }
New-Item -ItemType Directory -Path $workRoot -Force | Out-Null
$env:DATA_HOST_ROOT = $runtimeRoot
$env:STAR_ISLE_API_ENV_FILE = (Resolve-Path -LiteralPath (Read-Host '已准备好的 API 配置文件绝对路径')).Path
$env:CADDY_HOST_PORT = '8080'
$composeProject = 'starisle-local'
$privateWeb = Join-Path $workRoot 'web-private'
$webOverride = Join-Path $workRoot 'local-web.json'
$maintenanceOverride = Join-Path $workRoot 'maintenance.json'
$utf8NoBom = New-Object System.Text.UTF8Encoding($false)
```

先构建本地完整前端到维护目录，不覆盖公开站的 `apps/web/dist`。该目录明确只用于本地构建，重新构建会更新其中的文件：

```powershell
$env:PUBLIC_PRIVATE_AREA_ENABLED = 'true'
$env:PUBLIC_API_BASE = '/api/v1'
pnpm --filter @star-isle/web astro build --outDir $privateWeb
if ($LASTEXITCODE -ne 0) { throw '本地前端构建失败' }
$webConfig = @{ services = @{ caddy = @{ volumes = @(@{ type = 'bind'; source = $privateWeb; target = '/srv/web'; read_only = $true; bind = @{ create_host_path = $false } }) } } }
[IO.File]::WriteAllText($webOverride, ($webConfig | ConvertTo-Json -Depth 8), $utf8NoBom)
$composeArgs = @('--project-name', $composeProject, '-f', (Join-Path $repoRoot 'infra/compose/compose.yml'), '-f', (Join-Path $repoRoot 'infra/compose/compose.local.yml'), '-f', $webOverride)
docker compose @composeArgs config --quiet
if ($LASTEXITCODE -ne 0) { throw 'Compose 配置校验失败' }
docker compose @composeArgs up -d --build --wait --wait-timeout 150
if ($LASTEXITCODE -ne 0) { throw '本机栈启动失败，检查本项目容器状态' }
$localUrl = 'http://127.0.0.1:' + $env:CADDY_HOST_PORT
Invoke-RestMethod ($localUrl + '/api/v1/health/ready')
```

在浏览器访问 `$localUrl`，用所有者准备的密码登录。API/worker 共用 `DATA_HOST_ROOT`；模型 profile 未启用时，知识问答明确显示离线降级回答。正式 Pages 更新应另行执行公开构建和发布门禁，不上传这里的完整私有前端。

停止本项目使用 `docker compose @composeArgs down`，保留命名卷和外置数据。不要全局 prune、按端口杀进程或删除共享目录。

## 在 Linux 容器中备份和隔离恢复

API 镜像只打包应用，不含仓库 `scripts/`。在上节同一 PowerShell 会话内，增加仅用于维护的覆盖层：只读挂载两个恢复脚本和 API app，让 runner 根据脚本位置找到 API 目录；演练工作目录只挂到 `/drill`，与 `/data` 分开。不要挂载整个仓库或把实际数据根的父目录挂成 `/drill`。

```powershell
$drillRoot = Join-Path $workRoot ('drill-' + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $drillRoot | Out-Null
$mounts = @(
  @{ type = 'bind'; source = (Join-Path $repoRoot 'scripts/backup_restore.py'); target = '/workspace/scripts/backup_restore.py'; read_only = $true; bind = @{ create_host_path = $false } },
  @{ type = 'bind'; source = (Join-Path $repoRoot 'scripts/recovery_drill.py'); target = '/workspace/scripts/recovery_drill.py'; read_only = $true; bind = @{ create_host_path = $false } },
  @{ type = 'bind'; source = (Join-Path $repoRoot 'apps/api/app'); target = '/workspace/apps/api/app'; read_only = $true; bind = @{ create_host_path = $false } },
  @{ type = 'bind'; source = $drillRoot; target = '/drill'; bind = @{ create_host_path = $false } }
)
$maintenanceConfig = @{ services = @{ api = @{ volumes = $mounts } } }
[IO.File]::WriteAllText($maintenanceOverride, ($maintenanceConfig | ConvertTo-Json -Depth 8), $utf8NoBom)
$maintenanceArgs = $composeArgs + @('-f', $maintenanceOverride)
docker compose @maintenanceArgs config --quiet
if ($LASTEXITCODE -ne 0) { throw '维护配置校验失败' }
docker compose @maintenanceArgs up -d --no-deps --wait --wait-timeout 150 api
if ($LASTEXITCODE -ne 0) { throw '维护 API 启动失败' }
$execArgs = @('exec', '-T', '-e', 'PYTHONPATH=/app', '-e', 'DATA_ROOT=/data', '-e', 'DATA_HOST_ROOT=/data', '-e', 'PYTHON_DOTENV_DISABLED=1', 'api', 'python', '-B')
docker compose @maintenanceArgs @execArgs /workspace/scripts/backup_restore.py backup --data-root /data --output /drill/backup --verify --json
if ($LASTEXITCODE -ne 0) { throw '备份失败，不进入恢复阶段' }
```

选择一个备份中已知可命中的非敏感知识查询，从标准输入传入。候选须有至少一张可关联原图/缩略图的照片，以及至少一份 ready 知识文档和匹配的向量 profile。只包含文件、没有知识库或照片的备份可使用普通 verify/restore，但不符合 recovery drill 的完整数据要求。

```powershell
$knowledgeQuery = Read-Host '备份中已知可命中的非敏感知识查询'
$previousOutputEncoding = $OutputEncoding
try {
  $OutputEncoding = New-Object System.Text.UTF8Encoding($false)
  $knowledgeQuery | docker compose @maintenanceArgs @execArgs /workspace/scripts/recovery_drill.py --backup /drill/backup --target /drill/restored --report /drill/report.json --knowledge-query-stdin
  if ($LASTEXITCODE -ne 0) { throw '恢复演练失败，保留目标和失败报告' }
} finally {
  $OutputEncoding = $previousOutputEncoding
}
$drillReport = Get-Content -LiteralPath (Join-Path $drillRoot 'report.json') -Raw | ConvertFrom-Json
if ($drillReport.status -ne 'passed' -or (Test-Path -LiteralPath (Join-Path $drillRoot 'report.json.star-isle-recovery-drill-incomplete'))) { throw '恢复目标尚不可信' }
```

成功报告应为 `scope=isolated-local-candidate`、`productionAccepted=false`。它核对 SQLite、对象闭包、照片关联和恢复目标实际检索，但不启动恢复后的 Web/API/worker，不代替生产恢复验收。它也不包含运行配置、密钥或模型；这些由原本的本机配置独立提供。

如果失败，target/report/incomplete marker 可能保留。不要重用该目标、删 marker 后伪装成功或覆盖原运行目录。先保存失败报告并核对具体路径，另选一个新演练目录重试；需要清理时由所有者只处理确认属于本轮的路径。

## 恢复后切换和回滚

切换会暂停这个明确命名的本地项目。先在浏览器停止新的上传和写操作，确认所选备份/报告对应目标；保留原数据根、原 API 配置和相同代码/镜像。不要升级依赖或迁移数据库后再把失败归因于恢复。

```powershell
$originalRuntimeRoot = $env:DATA_HOST_ROOT
$restoredRuntimeRoot = Join-Path $drillRoot 'restored'
if (-not (Test-Path -LiteralPath (Join-Path $restoredRuntimeRoot 'db/star-isle.db'))) { throw '恢复数据库不存在' }
docker compose @maintenanceArgs down
if ($LASTEXITCODE -ne 0) { throw '本项目未停止，不切换数据根' }
$env:DATA_HOST_ROOT = $restoredRuntimeRoot
# 仅使用正常覆盖层启动，不把维护目录再次挂到新运行根旁边。
docker compose @composeArgs up -d --no-build --wait --wait-timeout 150
if ($LASTEXITCODE -ne 0) { throw '恢复栈启动失败，按下方步骤切回原根' }
Invoke-RestMethod ($localUrl + '/api/v1/health/ready')
```

从浏览器重新登录，核对已知文件能下载、照片原图/缩略图可读取、知识文档保持 ready 且原查询可检索。关键内容应与备份前已保存的受控样本字节/哈希一致。单纯 health 为 ready 或页面能打开不足以确认恢复完成。

若检查失败，停止恢复栈后切回仍保留的原根：

```powershell
docker compose @composeArgs down
if ($LASTEXITCODE -ne 0) { throw '恢复栈未停止，不继续回滚' }
$env:DATA_HOST_ROOT = $originalRuntimeRoot
docker compose @composeArgs up -d --no-build --wait --wait-timeout 150
if ($LASTEXITCODE -ne 0) { throw '原栈启动失败，保留两份数据和日志再排查' }
Invoke-RestMethod ($localUrl + '/api/v1/health/ready')
```

回滚不会合并恢复栈中后来新增的数据。因此恢复验证期间避免继续业务写入；原根、恢复根、备份与报告在确认前均保留，不自动删除。终端关闭后环境变量不会替你永久保存，下一次启动须重新明确项目名、数据根和覆盖层，避免连到错误目录。

## 操作依据

| 证据 | 结论 | 操作 |
| --- | --- | --- |
| `worker_runner` 独立消费索引与维护任务 | 仅启动 API/Web 不足以完成本地私有功能 | 开发模式保留第三终端；Compose 同时启动 worker |
| API Dockerfile 仅 COPY app，恢复 runner 使用脚本位置计算 API 目录 | 镜像中没有默认恢复入口 | 两脚本/API app 只读挂载，执行时使用 PYTHONPATH=/app |
| runner 的新目标/独立路径/marker 与只读检索约束 | 生成可信副本与启用服务是两个步骤 | 先独立恢复和检查，再停指定项目切换；失败切回原根 |

本指南未执行或读取你的真实运行数据。实际已覆盖项、受控失败记录和仍待外部资源的范围，统一见 [网站交付与本地恢复验收](./2026-11-03_网站交付与本地恢复验收.md)。
