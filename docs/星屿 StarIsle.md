## 1. 项目愿景

StarIsle（星屿）是一个个人品牌与私有数据入口的规划项目。“星”代表个人亮点与职业展示，“屿”代表由个人掌控的独立数字空间。公开面用于简历、项目、技能和授权媒体；私有面用于文件、照片、邮件和个人知识库。

目标不是一次性堆叠功能，而是在十周约 200 小时的个人开发容量内形成三个可独立验收的阶段成果。每个阶段必须先满足安全和质量门禁，再进入下一阶段。

### 1.1 项目目标

| 编号 | 目标 | 计划衡量方式 |
| --- | --- | --- |
| G1 | 建立可信的对外求职门户 | 公开页面可访问、移动端 Lighthouse 四项均不低于 90、仓库展示可追溯 |
| G2 | 建立单用户私有数据入口 | 私有 API 受 Cookie 鉴权保护，未授权请求返回 401/403，上传与邮件有安全边界 |
| G3 | 展示全栈与 AI 工程能力 | 三期分别留下可验收的静态、私有服务和 RAG 证据，而非只保留愿景 |

### 1.2 命名选择

| 候选名称 | 英文 / 仓库名示意 | 含义与定位 |
| --- | --- | --- |
| 星屿（推荐） | `StarIsle` / `star-isle` | 个人亮点与自托管数字岛屿，辨识度高且中英文通用 |
| 一隅 | `MyCorner` | 互联网中属于自己的一个角落，简约亲和 |
| 灯塔 | `Lighthouse` | 职业方向与归航主页，稳重清晰 |
| 数字花园 | `Digital Garden` | 持续耕耘的个人知识空间 |
| MeHub | `mehub` | 个人数据与服务的中枢，偏技术表达 |

首选名称为 StarIsle。域名、GitHub/Gitee 用户名、站点 URL 和硬件条件均未在本文预填；后续以配置项和实际可用性决定，避免把猜测写成事实。

## 2. 七模块与边界

| 模块 | 高层目标 | 阶段 | 关键边界 |
| --- | --- | --- | --- |
| 个人展示 / 求职 | 展示简历、技能、项目与授权作品 | 一期 | 无常驻后端依赖的静态部署，不公开私人数据 |
| 仓库展示 | 展示 GitHub/Gitee 公开仓库快照 | 一期 | 构建期分页抓取与 JSON 缓存；`featured` 来自本地配置，不冒充 Profile pinned |
| 自定义背景 | 浏览器中选择和保存个人背景 | 一期 | 仅 IndexedDB、同设备同浏览器持久化；不承诺跨设备同步 |
| 音乐播放器 | 播放自有、授权或公版样例 | 一期 | 先保证进度续播；保活是增强；不使用无授权媒体 |
| 文件 / 生活照 | 上传、浏览、下载、删除与照片时间轴 | 二期 | 随机对象 ID、SQLite 元数据、原件/缩略图分离、GPS 默认隐藏 |
| 邮件接收 | 在网页端安全查看来件 | 二期 | Cloudflare Email Worker 为唯一验收路径；Worker 以自定义 HMAC 转 FastAPI |
| RAG 知识库 | 对个人文档做带引用的问答 | 三期 | chat/embedding 两个内部模型实例；不公开模型端口；无 OCR |

以下不属于十周 MVP：博客、评论、书签、OCR、IMAP、复杂 Admin UI、多租户、Redis、复杂可观测平台、邮件发送和公共匿名文件分享。它们只有在总体具体计划的决策门触发后才可重新评估。

## 3. 高层架构

### 3.1 设计原则

- **公开与私有分离。** 公共门户优先静态、SEO 和性能；私有数据仅在受保护的 API 下访问。

- **单用户优先。** 鉴权、SQLite、存储与运维不为尚未提出的多租户需求过度设计。

- **渐进交付。** 每一期都有独立验收，避免七个模块同时开工。

- **隐私默认。** JWT 仅位于 Secure、HttpOnly、SameSite Cookie；上传、邮件和 RAG 都以最小暴露面设计。

### 3.2 目标拓扑

```text
浏览器
├── 公开静态门户：Astro + Tailwind + 必要的交互 Islands
└── 私有入口：同域 /api/v1
    └── Caddy → FastAPI
        ├── SQLite 与 StorageAdapter
        ├── Cloudflare Email Worker 的 HMAC 邮件接收链路
        └── 内部 llama-server（chat）与 llama-server（embedding）
```

一期默认使用 Cloudflare Pages。若账户条件不满足，只替换为 GitHub Pages；不并行维护两套静态托管站点。二期在私有 API 已就绪时才评估 Caddy 同域入口和 VPS/NAS 部署。具体目录、端点、配置、端口与迁移阈值由总体具体开发计划冻结。

## 4. 分期路线图

### 4.1 准备门槛

2026-08-27 至 08-31 是准备期，不计入十周。准备期只做范围、内容、配置、托管选择和验收证据设计的冻结；不把路径或命令当作已有实现。

### 4.2 三期计划

| 期次 | 时间 | 目标 | 阶段门禁 |
| --- | --- | --- |
| 一期：静态门户 | 2026-09-01 至 09-13 | 公开展示、仓库快照、背景、音乐播放器、SEO 与单一静态托管 | M1：移动端 Lighthouse Performance、SEO、Accessibility、Best Practices 均不低于 90 |
| 二期：私有服务 | 2026-09-14 至 10-11 | Cookie 鉴权、文件/照片、Cloudflare 邮件接收、Caddy、备份恢复 | M2：未授权 401/403、上传负例拒绝、邮件 60 秒内可查看、恢复演练通过 |
| 三期：RAG 知识库 | 2026-10-12 至 11-08 | 内部模型、文档入库、`sqlite-vec`、带引用流式问答、离线评测 | M3：至少 20 篇文档、回答有引用、CPU/ GPU 响应目标与恢复演练有记录 |

每周按约 20 小时规划。若某周少于 15 小时，保留 Must 与安全门禁，先延期视觉增强、播放器保活、语言占比、邮件体验、RAG 重排和悬浮入口；不得以新增模块解决进度问题。

## 5. 技术方向

| 层次 | 规划选择 | 原因与约束 |
| --- | --- | --- |
| 前端 | Astro、Tailwind CSS、React Islands | 静态内容性能优先；运行时交互只加载必要 JS |
| 后端 | FastAPI | 与文件解析、RAG 编排和 Python 生态相符 |
| 数据 | SQLite 起步 | 单用户、低运维；达到多用户/写锁/运维阈值后再评估 PostgreSQL |
| 模型 | llama.cpp / `llama-server` | chat 与 embedding 使用独立内部实例，不公开模型端口 |
| 向量检索 | `sqlite-vec` 起步 → Qdrant | `sqlite-vec` 是 pre-v1；仅在 chunks、延迟或并发阈值触发后迁移 |
| 邮件 | Cloudflare Email Worker → FastAPI | 原始 MIME 使用 timestamp、nonce、body SHA-256 的自定义 HMAC 认证 |
| 部署 | Docker Compose + Caddy | 二期起同域反代、自动 HTTPS、最小健康检查与恢复演练 |

参考项目只能用于借鉴公开的理念、边界和文档；许可证不等于允许直接复制实现。特别是 AGPL/GPL 项目只可借鉴行为与产品边界，禁止复制代码。

## 6. 风险与预算

### 6.1 主要风险

| 风险 | 高层应对 |
| --- | --- |
| 七模块并行导致范围失控 | 严格按三期与 Must/Should/Could；低于 15 小时立即裁剪 |
| 本地算力不足 | 先以 CPU 和小模型完成可引用闭环，再按评测和资源评估 GPU |
| 私有数据暴露 | 同源 Cookie、CSRF/Origin、随机对象 ID、上传验证、日志脱敏、恢复演练 |
| GitHub API 限流 | 构建期分页、版本化缓存、Token 只位于 CI/服务端 secret |
| 邮件滥用 | HMAC、五分钟时间窗、24 小时 nonce、Message-ID 幂等、HTML/远程图片控制 |
| 许可证或媒体授权问题 | 只使用自有/授权/公版媒体；AGPL/GPL 不复制代码；维护来源记录 |

### 6.2 预算参考

以下仅为个人量级规划估算，实际价格、硬件与域名由后续决策确定。

| 项目 | 参考范围 |
| --- | --- |
| 域名 | 约 60 至 150 元 / 年 |
| 入门 VPS | 约 300 至 1000 元 / 年 |
| 家用设备 | 旧主机 / NAS 利旧，电费约 10 至 30 元 / 月 |
| 对象存储冗余 | 个人量级通常低于 10 元 / 月 |
| 开源软件与模型 | 许可证成本可能为零，但算力、备份和运维仍有成本 |

最低可用规划为 2 核 CPU 与 4 GB 内存，适合验证小模型闭环；较舒适的 RAG 体验建议评估 4 核 CPU、16 GB 内存或至少 6 GB 显存的 GPU。任何硬件选择应以实际离线评测、容量与部署环境为准。

## 7. 验收与文档维护

阶段完成不以界面截图或命令存在为准。M1 要求 Lighthouse 四项不低于 90；M2 要求认证、上传负例、邮件时延和恢复记录；M3 要求至少 20 篇文档、引用、30 题离线评测与 CPU/GPU 响应记录。每项证据的输入、环境、期望与结果都应追加到总体具体开发计划的执行记录中。

变更规则如下：架构、API 根路径、阶段日期、安全边界、模型/向量策略变化时，先更新总体具体开发计划；随后同步本文与前端专项；真实实现状态只能在有可重复验证证据后标注。所有记录不得包含真实 secret、Cookie、JWT、HMAC、私人邮件正文或私人文件内容。
